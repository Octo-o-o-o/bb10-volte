# BB10 原生手机版完整实施方案

候选：2026-11-02，基于桌面 r14（6ca9147）。本文件是实施方案；未经实机验证的能力不得写成已支持。

## 目标与交付

同一仓库保留 Windows/macOS 桌面入口，新增 BB10 Cascades 原生应用。已 Root 用户可在手机完成下载、首次安装、激活、状态检查、换卡后的检查、更新、停用恢复、完整卸载与脱敏诊断导出。界面默认自动选择运营商，以一个随状态变化的主要按钮引导完成。保留原生拨号器、声音、短信、号码与运营商显示等现有能力。

交付包含原生 BAR、无需电脑的引导 ZIP、完整源码、可重复构建入口、中文和英文操作说明、升级/恢复与兼容性证据。桌面和手机共享设备引擎、载荷清单、原件散列和验收口径。不得把兼容性约束简单删掉以增加型号。

尚未 Root 的原厂手机仍需要现有电脑首次 Root 流程；手机版显示该前提。原生应用安装入口可以集成进现有首次 Root 完成步骤，但不把纯手机首次提权作为已经实现的能力。

## 一、证据与依赖

- 当前后台 `device/unified_service.py` 使用手机 Python 3.2，独立 fork/setsid 并忽略 SIGHUP；启动由 `device/unified_boot.sh` 和已识别 Root 入口负责。
- `device/unified_install.py` 已有 prepare/activate/update、旧配置迁移、原件备份、载荷校验及通话空闲检查；桌面 `tools/auto_carrier.py` 负责暂存、传输、备份下载与回执。
- AutoRoot v4 提供本机 installer、包内 pkg.bar、信任列表与启动阶段；作者文档：https://bb10.root.sx/blog/autoroot-v4 。本地原作者 install.sh 使用 `/pps/system/installer/upd/current` 安装 Term49。
- Root 不等于普通应用有 UID 0；__root/u_root、pathtrust 与安装器访问身份必须在实机核实。不得把默认 SSH 可用当成本机应用可用。
- BAR Installer 可以安装本机 BAR，但其本身并非在所有 Root 环境预装：https://barinstaller.online/ 。提供现有 Root 终端的引导路径解决首次入口。
- 原生 C++/QML 参考 BlackBerry 官方 Cascades 示例：https://github.com/blackberry/Cascades-Samples 。构建优先验证固定摘要的公开容器工具链：https://github.com/XIAZY/blackberry10-toolchain 。第三方 SDK/工具链不纳入产品源码包。

## 二、目录与边界

- `mobile/native/`：Cascades C++、QML、BAR 描述、图标引用、CMake 构建。
- `mobile/runtime/`：兼容 Python 3.2 的本机控制入口、安装事务、备份/导出、软件包验证、脱敏诊断、兼容性报告。普通 UI 不直接改无线配置。
- `mobile/bootstrap/`：专用离线引导程序与打包元数据，仅安装本项目原生应用，验证系统安装结果，不执行通用 Root 重装脚本。
- `tools/build_mobile.py`、`tools/package_mobile.py`：构建、校验、生成 BAR/引导 ZIP/更新包与回读报告。
- `tests/test_mobile_*.py`：共享接口、故障注入、恢复、包验证、桌面兼容、状态呈现。
- `docs/MOBILE*.md`、`materials/mobile-*.json`：流程、来源、验收与硬件支持记录。

业务引擎只有一份。新增手机管理代码不复制/改写 IMS 算法。数据和服务位于现有 root 私有目录；UI 的 BAR 升级或退出不会删除服务数据。必须区分界面卸载与完整停用恢复。

## 三、本机权限与控制接口

UI 调用有界的本机命令接口，固定动作包括 inspect/status/install/enable/disable/update/rollback/uninstall/export/compatibility。响应使用带 schema/version/action/operation_id 的 JSON。禁止从 UI 传任意 shell 命令。文件路径使用固定允许目录和经过校验的包名；拒绝符号链接、目录穿越、超长输入和不属于本次操作的临时文件。

首次调用探测实际 UID、QNX/ARM32、Python3.2、Root helper、pathtrust 和受保护 PPS 访问。只做读权限检查时不启停服务。Root helper 的 argv/stdin 行为须实机确认后确定启动代码，错误明确显示“Root 权限未就绪/此 Root 入口未适配”，不无限重试。App 获得 Root 后只运行经过验证的本项目代码；信任只授予精确文件，不信任整个根目录。

安装/更新操作使用全局互斥与事务标记，绑定准确设备与本次开机。关闭界面不取消已经提交的事务；重开后读同一事务。桌面和手机不能并发修改。现有桌面未识别到的新事务必须可发现并拒绝重复写入；不占用未知旧锁。状态查询不产生额外 IMS 启动。

## 四、首次安装与备份

原生 BAR 携带当前版本载荷和清单，不需在安装时下载固件、Python 或工具链。安装前重新核实设备、原厂文件、SIM、通话空闲、已安装版本、存储空间与包完整性。由现有 prepare 保存真正的原始配置；已安装用户保留第一份原始备份。

备份包含当前必需原件、清单及恢复信息，不携带无关用户数据。至少保留 root 私有副本和用户选定导出副本；优先 SD 卡，内部存储可用但必须明确其与系统同盘的恢复边界。导出后逐文件读回核验。手机与桌面备份记录必须明确来源、位置、清单哈希和验证结果；兼容历史 `desktop-backup-receipt.json`，不假称手机备份已经存在电脑。新增通用备份 schema 或兼容字段的确切方案由评审确定。

备份完成后 activate 提交安装和自启动。中断后按事务阶段恢复；无法判断操作结果时只检查，不重新执行写入。原厂 IMS 与补丁副本沿用现有检查，不覆盖原厂引擎。通话中不安装、切换、更新或恢复。

## 五、用户交互

首页只展示：设备与 SIM 的运营商、整体状态、一句原因、一个主要操作。状态应包括等待 Root、未安装、需要备份位置、正在安装、需正常重启、等待注册、已注册待通话验证、可用、需要第二次重启、已停用、恢复中、安装中断、版本冲突和设备待适配。

主要按钮依状态为“检查手机”“激活 VoLTE”“继续安装”“已重启，重新检查”“查看解决办法”。不让用户填写 IMSI、APN、IMPI、补丁地址等底层参数。安装/更新前显示将改变什么与备份位置；后续不重复无意义授权。系统授权与应用确认不混淆。

进度跟随实际阶段；不提供虚假的百分比。离线可以安装与管理，下载失败提供离线包入口。任何失败保留已成功的步骤。每次成功状态必须绑定当前启动、当前 SIM 和有效原生 IMS/LTE；“注册成功”与“实际通话验证通过”分开。通话验证由用户使用系统拨号器完成，不能自动拨号或制造收费通话。

高级页提供版本、当前引擎和机型支持等级、备份导出、脱敏诊断、停用/恢复、完整卸载、更新包导入。英文/中文、大小屏、键盘与触控都覆盖；长文本滚动，危险确认可取消，繁忙时不允许重复提交。

## 六、手机首次安装入口

A. 已有 BAR Installer：手机浏览器下载 BAR → 本机安装器安装 → 打开应用 → 检查 → 备份并激活 → 正常重启 → 检查和通话验证。

B. 只有有效 Root 终端：下载包含 BAR 和清单的引导 ZIP → 在现有 Root 终端执行固定本地命令 → 校验目标包 → 提交系统安装任务 → 观察同一任务的 success 并核实应用注册 → 桌面出现图标。优先验证 AutoRoot v4 installer/pkg.bar 机制；不假设写入 PPS 文件即安装成功。超时保留包和任务用于继续检查。

C. 已 Root 但没有有效终端或安装器：显示缺失条件及当前 Root 方案的恢复入口，不能从普通网页凭空取得系统执行权限。支持作者 Root 包预装本应用/引导器的集成方式。历史 v2/v3 按实际 helper 与启动机制分别适配，不强制重刷。

## 七、升级、回滚与完整卸载

更新包必须验证可信发布者的数字签名与全部文件哈希，不能只检查包内自带 SHA256。采用独立的产品更新签名，与 BB10 平台 BAR 签名分开；生产签名私钥仅存在维护者私有目录，测试与发布密钥隔离。明确首个安装包信任来源；旧 TLS/CA 无法验证时不关闭证书验证，提供离线导入。

在线检查仅读取小型版本清单；用户确认后下载。手机无网仍能导入已下载包。限制包大小、总展开量、成员集合、重复条目、路径、符号链接和压缩炸弹。校验完再写 root 私有暂存。版本与硬件绑定，任何回退都必须是受信任且兼容的已知版本。

服务升级沿用旧管理器停止/恢复 → 正常重启清理原生组件 → 备份并装新版 → 正常重启的真实状态机。UI 必须跨多次重启继续流程。现有 update 只允许有限 Python 文件集合，扩展前需明确兼容迁移；不得绕过其门槛。界面升级使用稳定应用 ID/author ID，不能在替换自身时丢失结果或恢复入口。

完整卸载先停用并恢复原始配置、检查恢复完成与重启需求，再移除本项目拥有且哈希匹配的启动入口/载荷；保留可导出的原始备份。未知文件、已有外部配置更改、活动通话或无法证明所有权时停止并给出明确原因。不得清理其他 Root 插件或共享目录。

## 八、兼容性扩展

现有 SQN100-3、SQC100-2、SQW100-4 / OS10.3.3.3216 / 三网 USIM 基线完整保留。手机端与桌面读取相同支持定义。现有已验收短信、声音、号码显示、换卡能力不能被手机 UI 降级。

新增设备采用能力检查与证据分层：识别到机型 → 原生映像/ABI和Root机制匹配 → 适配实现完成 → 实机功能验收。支持导出不含 IMEI/PIN/IMSI/号码/认证材料的适配报告，包含系统/型号/板型、原生文件哈希、架构、Root能力、SIM类型和服务可用性。

有现成证据的其他硬件变体继续核查；原厂文件相同也不自动等于射频、入网和恢复行为相同。可以明确给出“可研究适配”的结论，但只有满足已定义设备适配条件才能写入配置，只有实机证据才能标为已验证。不得添加“忽略检查继续”按钮。新机型不足的证据要精确列出，使后续补足不需要重新设计前端。

## 九、桌面共存与验证

- 手机创建安装后，桌面可识别、检查、备份和管理；桌面安装后手机可接管管理。接口版本不匹配时解释如何升级管理端，不覆盖未知状态。
- 完整桌面单元测试、manifest 校验、公开 allowlist 和离线发行检查继续通过。手机目录显式加入源码发布清单，不意外纳入密钥、SDK、原始设备日志和生成物。
- 自动测试覆盖：坏包/错签名/穿越/重复成员/错误机型；备份失败、写入失败、更新中断、重启边界；互斥、旧状态、UID或权限错误；脱敏与中英文状态；已有桌面与手机安装互相识别。
- 构建验证：原生编译、ELF ARM32/QNX loader/动态库检查、BAR manifest和资产回读、引导包回读、更新签名验证。
- 实机验证：本机首次安装入口；普通应用到Root；激活与正常重启；关闭界面继续服务；现有能力、两方向通话/声音/LTE、短信、换卡；更新失败恢复、停用与完整卸载。分别记录机型与版本，未测项不扩写。
- 设备写入先有已核实备份、空闲检查和明确目标；不因开发测试随意刷机、改基带或重启其他设备。

## 十、实施顺序与评审

1. 两位独立评审只读核查本方案、现有实现和证据，分别从事务/权限/恢复及兼容/体验/交付出发；交换发现并复核，先解决实质方案问题。
2. 验证最小原生构建和真实本机权限/安装机制；确认接口后并行实现本机管理、原生界面、构建/包/桌面衔接。
3. 执行完整测试与故障注入，构建可审查的安装包，再以真实设备完成能执行的验收。
4. 两位评审在实际候选上再次交叉核查。报告已经实现与验证的能力，以及确实需要其他设备/人工通话的剩余验收，不能用方案通过代替产品验收。

## 十一、第一轮评审后的具体协议（实施约束）

1. **共享回执**：新 `backup-receipt.json` 使用 schema 2，含 owner、installation_id/operation_id、source（desktop/mobile）、variant、backup_manifest_sha256、逐文件哈希、导出目的地类型/标识、逐文件回读结果。共享 `unified_service.verify()` 验证原件与回执；没有新回执时仍支持历史 desktop-backup-receipt.json。新桌面和手机均调用同一回执验证函数。手机内部导出明确标为 same_device，SD 卡为 removable；均不得声称已备份到电脑。
2. **共享互斥与持久事务**：新设备入口使用同一个 root 私有 POSIX 文件锁，进程退出后内核释放；锁与跨重启持久 journal 分离。读写入口均固定 Python/environment，明确清除 PYTHONOPTIMIZE、PYTHONINSPECT 等继承变量，保留 assert 检查。只读检查不取得写权限或改变 enable 标记。
3. **旧桌面边界**：原 r14 没有新锁，不能承诺与正在执行的旧 r14 写操作并发安全。首次接管已有安装要求维护阶段：先停止并恢复旧服务，正常重启，拒绝已有安装/更新 pending 和仍在运行的管理器。新 manifest 的文件指纹、新事务 phase 与严格的 before/after 校验使尚未开始的旧客户端在写前拒绝；用原 r14 入口验证此拒绝行为。以后完整并发互斥仅对新版桌面/手机版保证。不能把“旧hash不匹配”描述为能中断已越过验证的旧进程。
4. **首次安装中断**：原子认领 BASE 后，先写 preparing-v2 所有权记录；先持久化原件/intent/哈希，再写候选载荷。恢复只使用已记录的原件，从未提交无线更改的阶段才允许补齐缺失采集。activate 使用 write-ahead journal，先记期望前后字节与精确路径，再逐项创建启动入口；中断后只接受 before/after 之一，未知内容停止。v2 btool 保留 inode/ACL，v4 addon 逐个文件和目录记录所有权。断电恢复不得重新把变更后的配置认作原厂备份。
5. **更新/回滚**：备份旧Python、manifest和enable状态在替换前完成，逐文件回读，manifest最后提交。保留正常重启清理原生组件的门槛。回滚只使用同一安装归档中已验证的旧文件，允许旧/新混合但拒绝第三方字节；不能循环启动/结束原生IMS来模拟恢复。自动续接事务前核对同一设备与包摘要。
6. **卸载**：先停止服务、等待恢复，再正常重启，核对无残留自有原生/VPN/软件提供器及DCA/PPS还原。仅移除具有所有权与哈希证据的文件和hook，保留原件备份。发现未知成员不能递归删除，也不能把整个 BASE 移走而声称完整卸载；应保留并明确报告。
7. **发布信任**：使用 RSA-2048 或更强、PKCS#1 v1.5/SHA-256，对包中 manifest 的精确 UTF-8 字节签名；Python3.2 verifier 固定允许的算法、长度、填充和公钥，不执行包内 verifier。公钥固定在版本化应用和 root 控制代码内，生产私钥只在维护者私有目录。SHA256只能证明完整性，不能替代发布者签名。共享目录输入复制到本项目 root 私有暂存，验证该副本并在执行前复核；不直接以Root执行可由其他应用改写的输入。测试密钥不进入发布信任列表。
8. **本机入口**：v4 helper和系统安装接口需实测；v2/v3按能力及已核实脚本分别登记，未知入口不写入。bootstrap 超时保存任务，继续查询同一任务，而不是重复提交。基础环境缺少入口时明确说明原因，不能假装无条件一键。
9. **原生构建**：固定容器digest，遵守目标Qt4.8/Cascades和gnu++98 ABI，不使用Qt5/6 API。首个BAR验证ELF QNX loader、ARM32、动态依赖和平台manifest。维护稳定 App ID/Author ID；两版BAR替换验证不丢任务/备份，不能从单次编译成功推断安装/升级成功。
10. **真实状态**：读状态时重新核对当前SIM与选择记录，过期状态不得显示可用；用户通话验收记录绑定本次启动/SIM/载荷版本，与IMS注册区分。敏感字段用于机内比对不回传UI或诊断导出。
11. **不支持设备报告**：独立只读采集入口先于安装准入，逐项捕获失败并保留经长度/字符校验的未知板型；不复用会提前抛错的 installer.identity 作为全部采集。报告将Root、OS、ABI、原件散列、SIM、硬件/功能证据分项呈现，给出缺少项。现有SQC100-4证据没有建立真实适配，不能列为已支持；报告机制为后续适配提供输入。
12. **交付状态与版本**：手机管理协议版本为2，对应本次新构建桌面；r14及更旧桌面只保证被新载荷明确拒绝，不能称为可完整管理。UI与下载页按能力说明三种首次入口，不能依赖尚未装好的App告知无法安装。支持表区分r7/r8历史九组合语音、r14两组合短信、新管理版本/Root与未测项。更新工作进程从已校验的root私有快照运行，不能依赖正在被替换的BAR资产目录。

这些是对方案的明确化；只有对应实现与测试通过才记录为交付。首次Root、未知硬件和系统无法启动时的救援边界沿用正文，不因用户希望全面支持而伪造实机结果。
