# Q10、Classic / Q20、Passport 全后缀适配方案

调研日期：2026-11-02。发布基线：`v0.5.0-r14`，源码 `6ca9147732575617dfeb2019ae4fdd680f014734`。本文件区分发布现状、当前分支已经实施的修复、后续需要真机的适配；本分支没有发布新的 EXE / DMG。

## 1. 目标与结论

目标是让每个后缀在进入流程时都有明确结果：能开通的走完整流程；有条件可适配的指出缺口；硬件或网络不匹配的在下载、刷机、清空数据之前说明。当前范围为 Q10、Classic、Passport，中国移动/联通/电信，Windows x64、macOS 14+ Apple Silicon / Intel。其他国家运营商和 Linux 桌面版需要独立计划。

不能把“全后缀有处理路径”表述成“全后缀三网均可通话”。软件目录有 14 项，厂商认证材料可确认其中 13 项；`SQW100-2` 仍待核实。现有自动 VoLTE 只接受 `SQN100-3`、`SQC100-2`、`SQW100-4`，三个网络是 `460-00 / 460-01 / 460-11`，并要求 OS `10.3.3.3216`、无 ISIM 的 USIM、原生文件指纹及运行状态匹配。代码依据：[carrier_policy.py](../device/carrier_policy.py)、[unified_service.py](../device/unified_service.py)。

完整机器可读调研快照见 [variant-coverage-research-2026-11-02.json](../materials/variant-coverage-research-2026-11-02.json)。用于桌面前置说明的目录是 [device-support.json](../materials/device-support.json)，它不会代替手机上的授权条件。

## 3. 镜像、加载器和配置是否齐全

### 3.1 已经有的材料

- 三个家族的原版固件、AutoRoot v4 已在本地找到并重新验证完整 SHA-256；14 个目录条目均能解析到镜像配方。
- Q10 与 Passport 使用归档包，Classic 使用 STA100/Z30 命名的 EXE；匹配依据必须是材料清单、内容和目标硬件，不能只看文件名。
- 每个家族均固定原版系统分区、radio 指纹；个人密钥在用户电脑上生成。EXE / DMG 不包含完整原版固件或可共享的个人 Root 镜像。
- 四个运营商 JSON 通过结构校验，但“模板存在”不等于自动开通或实机验收。附加 MNC 02/07/09/03 目前仍不能等同于自动流程的 00/01/11。

清单见 [sources.json](../materials/sources.json)、[stock-partitions.json](../materials/stock-partitions.json)、[first-run-tools.json](../materials/first-run-tools.json)。这些清单中的 `manufacturer_signature_verified` 是 false；本地哈希相符证明与已固定材料一致，不证明厂商已经为每个后缀验证。

### 3.2 加载器是独立的缺口

本次只读解析固定 AutoRoot 包中的 `loaders.dat` 和 `cap.exe`，没有执行固件、没有连接手机：

- 82 个归档加载器中，81 个的压缩流 CRC 与解压长度匹配。
- LDR_00 的偏移为 10，落在归档头内，CRC 不匹配；r14 已针对 `9400270a` 从固定 cap.exe 提取完整加载器，保留 gzip CRC、文件 SHA 校验，已有 SQC100-2 / ARM64 实机记录。
- cap.exe 有 213 个描述项，其中 96 个内嵌加载器通过 gzip CRC；这不代表 213 个硬件型号均可用。
- 固定映射及定向修复中没有 `9500270a / 9600270a / 9700270a / 9c00270a`。若目标实际报告这些 ID，现有 Mac 查找路径不能因为型号选择框有该后缀就自动成功。ID 与后缀必须由目标机只读身份补证，本方案不把论坛对应关系当授权。

核对了上游最新提交，仍为固定的 `d45b66b`。依据为 [加载器映射](https://github.com/bb10root/bb10mt/blob/d45b66ba9594a2912dd005e3607da1d4825fb06e/bb10mt.ini)、[精确 ID 选择逻辑](https://github.com/bb10root/bb10mt/blob/d45b66ba9594a2912dd005e3607da1d4825fb06e/ramloader.pas)、[归档 CRC 实现](https://github.com/bb10root/bb10mt/blob/d45b66ba9594a2912dd005e3607da1d4825fb06e/uarchive.pas)。Mac 查找结论不能直接外推 Windows 自包含 autoloader。

修复方向是建立 `硬件 ID → 固定来源 → 精确加载器 → SHA/CRC → 主机平台 → 实机验收` 的记录，先校验再加载。不能把未知 ID 随便映射到 SQC100-2 的加载器，也不能关闭 CRC 或尝试逐个加载器碰运气。

### 3.3 配置不能按后缀简单复制

自动引擎除了四个旧预检文件，还校验 qct_rrm 和 dca，共六个原生文件；另有 helper 指纹。每个新型号需核对同一 OS 下这些字节是否一致。相同才能评估复用补丁，不同则需要新的原生引擎与验证，不能增加一个哈希即放行。

SIM 必须按实际 HPLMN、USIM/ISIM 路径、当前 stock carrier 模板与 APN 关联。不能按运营商显示文字、电话号码段或漫游访问网络选择配置。历史 ITU 汇总表本轮未能提供足够新的国内完整 MNC 分配证据，因此额外 MNC 应结合当前运营商资料和真实卡的脱敏报告逐项登记，不声称现有七个模板 MNC 已覆盖全部卡。

上游 [VoLTE Addon](https://bb10.root.sx/blog/volte)与本项目不是同一个安装器；上游提供的三个运营商模板含 Vodafone Ukraine、联通、移动，不含电信。上游模板与 [AutoRoot v4](https://bb10.root.sx/blog/autoroot-v4)的包结构可用于理解图 2，但不能证明本项目或所有后缀已被修复。

## 4. 本分支现在落实的前置处理

当前修改按照“已有证据的能力全部接入；没有适配的在前面说明”实现：

1. 14 个目录条目都有明确分类；前三个已适配后缀继续使用原流程。其余按“可研究”“已知频段不匹配”“身份待核实”显示原因，不返回一个笼统的连接错误。
2. 首次使用和连接页面显示准确后缀的支持范围。Root 页可选择计划使用的运营商；说明出现在可滚动操作区之外，不必滚到底才看到。
3. 默认目标是开通 VoLTE。未适配型号在下载、浏览器下载、固件导入、Root 镜像构建及刷写前停止；直接调用按钮处理函数也会检查，不能仅靠置灰。
4. 用户如果确实只做原版恢复或独立 Root，可明确选择“仅准备或恢复系统 / Root，不开通 VoLTE”。这不增加 VoLTE 权限，仍保留型号绑定、系统版本、镜像指纹、连接及清空确认。SQW100-2 等身份未核实项不能通过该选项放行。
5. 系统升级入口使用相同限制，防止绕路进入大文件下载或清空数据。读取既有记录和已写入后的版本回读仍保留，不能因新增提示破坏恢复工作。
6. 已 Root 手机的自动适配检查，对型号、OS、主板冲突和原生文件不匹配返回结构化原因；SIM 不受支持时取消首次安装资格。
7. 桌面安装器在建立原始备份、接替旧服务之前复查 `can_install` 和 `sim_supported`。实际 SIM 在检查后变化，手机端仍重新核对，旧检查结果不能作为安装授权。
8. 先前截图修复继续保留：Root 页重新检测入口；临时读不到型号时保留已生成镜像；真正换成不同手机仍清除当前选择并要求重新确认。

本次没有扩大 `carrier_policy.MODELS` 或 `CARRIERS`。19 个额外射频候选缺少逐后缀的原生指纹、加载器、生命周期和实机记录；把它们直接加入自动启动会把未完成的适配隐藏成支持，无法满足“不要最后才失败”的要求。

## 5. 进一步增加适配的实现步骤

### A. 先完成只读候选采集

每个新后缀只读获取：系统完整型号、监管型号（如可读）、Board_Type、BootROM hardware ID（有非写入读取路径才取）、完整 OS / radio 版本、六个原生文件 SHA、Root 方案与有效 UID、USIM/ISIM 类型、HPLMN、stock template ID/hash、LTE 能力与当前数据连接、旧服务归属和当前启动状态。

复用现有有界 PPS 读取与隐私过滤。频段位图保留原始值与解析版本，不能未经定义就把某个整数当成 Band 编号；缺失值标为未知，不填 0。报告不包含完整 IMSI/IMEI/ICCID、私钥、认证材料或短信内容。先补充未知 Board_Type 的有界观察能力，再维护已核对映射；不能因为名称未入白名单就丢掉所有研究信息。

输出：每个后缀一份可复核证据记录，明确“资料证据”“用户报告”“离线验证”“本项目实机验收”，带工具版本、候选提交和日期。

### B. 镜像与 Root 逐项闭合

文件：`materials/sources.json`、`materials/stock-partitions.json`、`materials/macos-root-tools.json`、`tools/root_images.py`、`tools/macos_root.py`、`tools/root_flash.py`。

- 验证原始容器的设备目标、OS 与 radio 版本，并交叉核对实际硬件 ID；家族共享内容可以去重存储，验收项不能合并。
- 每个后缀保留 stock 恢复、Root 构建、OS 写入、radio 写入、开机读回、新密钥有效 Root 的独立状态。
- 不复制他人的密钥；AppWorld 触发条件明确展示。加载器必须匹配实际 ID 并完整校验。
- 保留当前严格刷写结果分类；退出码 0、最后一行成功或上游笼统“忽略错误”均不能代替完整写入证据。
- Root 是独立目标：能 Root 但不能在所选网络 VoLTE 的型号，也应在最前面明确告知。

### C. 引擎复用与新型号适配

文件：`device/device_info.py`、`device/carrier_policy.py`、`device/unified_service.py`、`device/unified_dca.py`、`device/unified_migrate.py`。

- 身份、原生文件及已研究状态完全一致的后缀，优先复用现有引擎，增加精确 variant/board 记录；差异必须成为独立分支。
- `unified_migrate.BASES` 只有三个旧安装目录。新机型无旧安装时应明确走干净安装；发现其他工具时返回冲突说明，不能因字典缺项崩溃，也不能猜测删除 `/var/addons/volte`。
- Q10 / Classic / Passport 与运营商的 DCA、语音策略、提供器寿命需要单独核对。Passport 的提供器保留至正常重启策略不能被一个“实验试用”开关绕过。
- 初始实机试用不启用自动启动；完成启动、停止、恢复和正常重启后才升级能力等级。旧手动实验入口和统一自动服务应在文案与能力记录中区分。
- 新增任何手机载荷文件都需升级 `PAYLOAD_FILES`、包清单和更新协议。现有更新只允许固定文件集合，不应为了兼容旧包放松任意文件覆盖。测试 r14 → 候选、每个更新中断点、继续处理和恢复。

### D. 运营商和短信

- 先完成当前三个 PLMN，再逐项扩展已有模板的 02/07/09/03；每个实际卡类型单独记账。ISIM 是独立认证路径，不能简单取消拒绝条件。
- 将入网失败、LTE 频段/覆盖不足、数据 APN 未建立、IMS 认证失败、通话失败、SMS ACK 关联失败分开呈现。
- IMS 200 OK 只证明注册；至少还需呼入、呼出、双向声音、通话保持 LTE、挂断、正常重启及短信验收。
- 短短信、分段长短信、两条内容完全相同但独立发送的短信要分别验证；不能用内容去重掩盖重复投递。

### E. 产品说明与发行一致性

让前置目录、自动策略和验收记录有一致性测试，生成支持表和发行说明。历史 `COMPATIBILITY.md`、`AUTO-CARRIERS.md`、`ISSUES.md` 的旧范围应标出时间和旧入口，不能继续作为当前统一服务的总说明。官网和包内帮助必须使用相同的发布快照；源码修复不等于已下载用户的 r14 自动更新。

## 6. 实施优先级与完成条件

| 阶段 | 工作 | 完成条件 |
|---|---|---|
| P0 | 本次前置说明、下载/刷写入口拦截、SIM 安装资格修正、截图向导修复 | 当前三后缀不退化；其他后缀在准备前得到可读结论；单测和打包检查通过 |
| P1 | 优先采集图 3 的 SQC100-3，以及已有反馈的 SQC100-4 | 真实身份、原生文件、LTE 入网、旧安装状态、加载器缺口可判定；SQC100-4 优先联通/电信 |
| P2 | SQC100-1/-5、SQW100-1/-3 复用候选 | 在指纹一致前提下逐个完成受控手动验证，再逐个启用自动服务 |
| P3 | SQN100-1/-5 的电信 B5 场景 | 当地实际 LTE B5、SIM 与原生引擎都通过；不宣传三网 |
| P4 | SQN100-2/-4、SQW100-2 | 前两者保留独立 Root/其他地区说明；后者先核实身份，未核实不刷写 |

不要用排期代替验收。代码可先完成，何时宣布新后缀支持取决于相应设备和 SIM 的证据，而不是“同一家族应该差不多”。

验收矩阵：

- 离线：14 个条目 × 3 个运营商都有明确结果；未知型号、错主板、未知/错误 OS、ISIM、缺失 SIM、未知 MNC、篡改原生文件、模板缺失、两个 USB 手机分别停止在对应阶段。
- Root：如果宣传 13 个已确认后缀在 Windows x64、Mac ARM64、Mac Intel 都能首刷，应补齐 39 格真实首刷证据。少量代表机测试只能证明对应格，不能声称交叉组合全部通过。
- 语音/SMS：28 个射频候选逐格验收；11 格无交集标“不适用”，SQW100-2 的 3 格标“身份待核实”，不得计成通过或失败修复。
- 换卡：每台支持多运营商的设备覆盖所有适用的有向换卡路径、正常重启、待机来电、关闭/开启服务；断连、异常退出、备份校验失败和未知更新状态验证可恢复。
- 稳定性：建议双向通话各至少 2 分钟，正常重启至少 3 次，至少 24 小时观察；这是新验收目标，不是既有 r14 已完成的结果。
- 平台：实际 EXE / DMG、干净用户目录、无外部 Python、中文路径、代理下载、离线导入、低磁盘空间、系统缩放、Intel 与 ARM64 原生运行分别记账。

现有 r14 的历史证据是 9 个语音/换卡/显示组合；本轮新 SMS 证据只有 SQC100-2/联通与 SQW100-4/移动。短通话约 7–10 秒、短信尾部至少观察 180 秒，不能直接当成上述新稳定性目标。证据见 [unified-carrier-acceptance.json](../materials/unified-carrier-acceptance.json)、[sms-device-validation-2026-11-01.json](../materials/sms-device-validation-2026-11-01.json)、[Root 验证记录](../materials/root-workflow-validation-2026-11-01.json)的 follow_up_acceptance。

## 9. 与原生手机版的关系及本轮取舍

2026-11-02 用户确认暂时没有新增后缀的真机可配合，要求先尽可能完成准备。本轮随后只读查看了“确认项目能否在 BB10 独立运行”会话的方案、`feat/native-mobile-20261102` 分支工作区和正在编写的代码。它基于同一 r14，正在实现 Cascades 原生应用、本机引导、共享安装事务/备份回执及只读适配报告；**尚在实施中，不是已通过验收的手机发行版**。没有修改该工作区或操作它正在使用的手机。

手机版值得做，也不替代硬件适配。它减少已 Root 用户的电脑/USB/SSH 依赖，改变安装和管理入口；频段、SIM、系统原生文件、IMS 及提供器生命周期仍来自同一部手机。未 Root 用户的首次刷写、系统无法启动时的恢复仍需要桌面工具。

| 工作 | 手机版完成后的价值 | 当前分工 |
|---|---|---|
| 完整后缀、射频与运营商候选矩阵 | 两端都必须在开通前说明 | 本分支完成资料与前置目录，手机版复用 |
| 原生映像、SIM、OS、主板和恢复检查 | 两端共用，不能因手机安装而略过 | 本分支修正现有 probe/安装前检查；与手机事务一起合并 |
| 首次 Root、固件/加载器校验 | 原厂用户和救援仍需要 | 保留桌面修复与材料证据，逐后缀补实机验收 |
| 已 Root 用户连接电脑后安装/更新 | 手机可减少这条路径的使用 | 维持兼容与必要修复，不重复开发手机管理功能 |
| 本机安装、升级、互斥、备份、恢复和导出 | 手机专属入口但共享底层 | 由手机版分支实现，本分支不复制一套 |
| 新后缀只读采集与手动实验入口 | 便于后续寻找测试者 | 复用手机版正在实现的报告；现有旧手动入口的条件不等于自动支持 |

### 9.1 接入契约

1. `materials/device-support.json` 是前端可共用的硬件资料，已有 14 个条目；`tools/device_support.py` 是桌面适配层，依赖桌面路径与翻译模块，**不要把该模块直接搬到 Python 3.2 手机环境**。手机端从其受信任包内读取同一 JSON，用 `device/carrier_policy.py` 决定实际安装资格，不能在 QML/C++ 另写宽松白名单。
2. 前端分类为 `model_required`、`model_unconfirmed`、`radio_no_overlap`、`adaptation_pending`、`supported`。这里的 `supported` 仅表示型号和计划运营商已在自动策略范围内；Root、真实 SIM、原生散列、备份、事务及通话状态还需实际检查。计划选择的运营商不能覆盖真实 HPLMN。
3. 手机 `probe()` 的新增拒绝结果保留 schema 1，并含 `scope_error`、`can_install=false`、`can_update=false`、`sim_supported=false`。当前拒绝路径没有检查已安装状态，`installed=false` 不能被用于展示“确认没有旧安装”或决定删除旧目录。应先显示阻断原因；手机版的独立报告再逐项只读采集。
4. 首次安装必须同时通过 `can_install` 和 `sim_supported is True`；手机控制入口也要重新执行实际检查。已安装载荷的停用、恢复和可接受更新有独立条件，不能把 SIM 阻断错误地变成禁止恢复。
5. 将同一 JSON 纳入手机版签名包的成员及哈希清单。在包回读测试中核对内容与桌面一致，复用 42 格矩阵断言（9 个当前自动组合、19 个待适配、11 个无国内已核对频段交集、3 个身份未知）。实验模式必须独立说明其条件，不能把它计入 9 个正式自动组合。

### 9.2 合并时必须保留的行为

两个分支都修改 `device/unified_install.py`；手机版正在扩展备份回执、事务和中断恢复，不能用本分支整文件覆盖它。合并需按行为保留：型号/OS/原生文件的结构化拒绝、SIM 拒绝时取消安装资格、手机新增的锁与持久事务、旧备份兼容。`tools/auto_carrier.py` 之后也可能与手机桌面共存改造重叠，必须在最终版本重跑安装/更新和故障注入测试。

`materials/unified-payload.json` 应在合并后的文件上重新生成，不能手工选择某个分支的旧哈希。已发布 r14 的精确载荷指纹可保留为迁移依据；本轮未发布的中间载荷不应为了方便更新而被宣称成正式版本。手机版协议升级对旧桌面的约束以最终共享协议为准，不能因本分支仍能测试 r14 而许诺旧 r14 可管理新手机版安装。

四张图片的收益也不同：图 1 的电脑连接步骤对已具备有效 Root/本机入口的用户可以被手机版省去；图 2 的本机引导报错需由新引导器根据权限、路径、真实安装结果解释；图 3 的 SQC100-3 兼容性限制两端都存在；图 4 的首次 Root 准备与刷写仍属于桌面流程。因此保留本轮前置检查和 Root 修复有直接价值。

### 9.3 无新增真机时的完成边界

现在可以完成资料核实、材料内容/指纹审计、42 格前置处理、安装前拒绝、错误解释、模拟回归和合并说明。本轮已完成这些工作。新后缀的实际板型、BootROM ID、权限入口、双向声音/SMS、原生停止恢复与重启行为需要真实设备补证；当前没有这些输入，不能编造映射、取消散列校验或把未验证项标成成功。

后续测试者先用手机版的独立只读适配报告或同契约桌面报告采集，不要求先清空重刷。建议先找 SQC100-3、SQC100-4（联通/电信）、SQW100-1/-3，再按第 6 节逐格推进。这样新增实机到位时只补对应差异和验收，不必重新设计两端界面。
