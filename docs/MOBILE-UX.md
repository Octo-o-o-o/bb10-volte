# Native mobile interaction contract

The Cascades UI in `mobile/native` uses Qt 4 and C++98. The implementation is a client of protocol 2; it does not infer Root access, carrier readiness or installation eligibility from an icon, network label or an earlier UI step.

Current installed acceptance target: mobile **0.1.0.12 / desktop r18**. Passport full lifecycle and Q20 migration voice/SMS acceptance are scoped in [validation](MOBILE-VALIDATION.md); later source changes have not replaced those artifacts. The owner accepted the isolated Passport wake/reset event without a root-cause claim. v7 fixed Cascades property shadowing, v8 added automatic reboot reconciliation and v9 added foreground waiting for delayed Root startup.

## Home and tasks

Home shows the hardware, carrier, current state, reason and one primary action returned by the runtime. First activation exposes the backup destination before confirmation. An available SD card is preferred on first use; internal storage remains possible and is explicitly described as a copy on the same phone. The runtime chooses the exact owned export path and performs readback verification.

Device mutations return a persistent job identifier. The app saves that identifier and polls the existing job, displaying translated stages without inventing percentage progress. Closing the UI does not cancel the Root worker. Reopening resumes a query, never a second install command. A timeout preserves the operation identifier and asks the user to check the unknown result. Restart instructions come from device state rather than a UI restart counter. A second carrier-policy restart is distinct from installation or service-update restarts. Completed tasks trigger a fresh status read and retain the last exported backup/report location. The manual call record is a synchronous, guarded response with no background job.

Post-v12 source addresses a Q20 save-feedback failure: the four checks were saved, but the UI did not confirm the result until reopening. Saving now returns the observation already validated under the management lock instead of repeating a full probe after the write. A missing response triggers one read-only check when the app is foregrounded, never another save. The pending confirmation type and opaque context survive reopening; only a matching verified response resolves that confirmation. A different boot, SIM or payload cannot inherit the old check, and another management task cannot erase the unresolved confirmation. Saving and checking have distinct bilingual progress messages. This behavior still needs acceptance on its new BAR.

On QNX, the mobile worker uses the dedicated `SPAWN_NEWAPP` launcher. A controlled Passport probe verified `appid = sid = pid` and completion after the parent exited; ordinary fork/setsid alone is not the application-lifecycle guarantee. Closing and reopening the real app still requires the separate UI acceptance check. Existing tasks survive app replacement. v8 automatically completed a pre-existing stop task after a real reboot and then offered the bundled update; the owner also completed that update through the native UI.

Registration and verified calls remain separate. The call page asks the user to complete outgoing and incoming calls, hear audio in both directions and observe LTE. It records the four explicit checks without placing calls. The backend binds the record to the current SIM, boot and payload; a SIM/boot change invalidates usability independently of the UI. The client submits the four booleans at the top level of protocol 2 along with `confirmed` and the opaque `call_context`, and clears the checkboxes whenever that context changes.

## Management, offline access and recovery

The management page provides language, backup destination, offline ZIP selection, update check, diagnostics, compatibility, enable, disable/restore, rollback and full uninstall. The system file picker only supplies a path; the runtime still copies and verifies the package in its private directory before use. Online metadata and downloads use HTTPS with normal certificate verification and an explicit project-domain allowlist. Download size and hash checks do not replace the runtime's publisher signature verification. Update comparison uses the active runtime version when available, because payload updates and BAR replacement have separate identities. No online access is required for the bundled installation or offline update path. Diagnostics and compatibility reports may return synchronously without taking over a pending write job; their exact exported location remains visible on Home and in management details after reopening the app.

When an old r14, r15, r16 or r17 service is stopped, restored and ready to update, the home primary action and management page offer the **bundled update**. It applies the signed payload already in the BAR without choosing an offline ZIP. Ordinary ZIP updates require a newer runtime version; selecting the same-version ZIP is not the old-engine adoption path. Each r14/r15/r16/r17 → r18 path needs its own end-to-end acceptance.

Destructive operations use a cancellable system confirmation describing the changes and required restarts. Button eligibility comes from the runtime's action list. While a job is running the UI does not submit another mutation. Full uninstall is a restoration workflow; deleting the app icon alone is not represented as service removal.

The separate experimental page has 23 explicit options: four existing carrier profiles (`china-mobile`, `china-unicom`, `china-telecom`, `china-telecom-46011`) and 19 exact-variant trial profiles/catalog entries generated from the shared desktop definitions and signed in the bundle. The trials comprise 13 controlled manual candidates and six read-only Passport combinations. Generic legacy profiles are limited to SQN100-3, SQC100-2 and SQW100-4; every other variant requires its exact trial. The page sends `experimental=true`, explains the lack of hardware acceptance and leaves autostart disabled. Changing a profile clears prior eligibility and requires a fresh check. Every legacy start independently rechecks compatibility and the installed profile. A completed experimental task refreshes its selected profile. It is never the normal activation button; native hashes, ABI, current SIM, network and recovery remain backend gates.

Legacy controls have their own scope. `legacy-stop` disables the old autostart entry and waits for restoration. `legacy-update` requires a stopped/restored installation and no pending install-transaction before calling the existing updater; interrupted transactions remain and blind retries are rejected. `legacy-uninstall` removes legacy startup entries while retaining private payloads/backups. It is not automatic protocol-2 full removal, and no legacy rollback is offered. The 13 ordinary trials have no Telecom attach modification: their restoration source is the PPS journal captured at startup, not an automatic protocol-2 original-file export receipt. Exported trial results are labelled `last_checked_not_live`, not presented as live status or call acceptance. Read-only Passport options do not expose mutations.

## Language and screen behavior

Menus, Root/transport errors and confirmations have Chinese and English strings in `src/ui_strings.h`; runtime state text uses the requested language in its display model. Language changes trigger a fresh read when idle. Every content page scrolls vertically, body and error labels wrap, and diagnostic text is plain text. The UI uses full-width actions, normal Cascades focus behavior and the R refresh shortcut. Confirmation can be cancelled through the system dialog.

Acceptance must cover the Q10/Classic smaller square screen and Passport larger square screen in both languages, physical keyboard/trackpad navigation where present, touch, long messages, FilePicker cancellation, Root unavailable, backup selection, installation interruption, both restart stages, offline update failure and reopening an existing task. Compile or static-contract tests do not establish those physical UI results. Added portrait devices require their own layout and functional acceptance.

## Build and trust

The BAR identity is `com.octolab.bb10volte`, author `OctoLab`, with a fixed author ID. The build pins the entry script SHA-256 into `bundle_identity.h`; the UI checks the original bytes before invoking `/bin/__root`. It sends those exact bytes through a literal, collision-checked heredoc into an exclusively created random Root-private directory. Only that private copy is pathtrusted and executed; the app's writable source path is never reopened as executable code after verification. The source assets directory is passed as data for the entry's independent signed-bundle verification. The helper receives a fixed minimal environment, an allowlisted action and base64 JSON. Cleanup unlinks only its own entry and removes its own empty directory. Device Python runs from a trusted file, not stdin. Entry source must end with LF and contain no NUL so the literal transfer preserves its bytes. An incomplete UI-only build has no valid entry hash and refuses device operations.

Build checks include ARM32/QNX ELF, libraries, BAR identity and assets. v6 through v10 have matching SUD success and actual registered versions; future candidates still need independent verification. Runtime payload and native application versions are separate.
Automatic status checks run only in the foreground: active jobs about every 1.8 seconds, network waiting about every 10 seconds, and reboot waiting about every 25 seconds after the previous reply. Root unavailable during observation shows a waiting state and retries reads every 10 seconds. Background and sleeping states pause checks; confirmations, file selection, and experimental results are protected. Unknown write outcomes never trigger automatic resubmission.

Before process startup, the unsigned BAR depends on AutoRoot launcher initialization. The app cannot render a waiting page while the OS refuses its launch. v10 restart instructions and bootstrap documentation require the system Root success notification before opening once. Repeated early launches produced an observed Navigator deadlock; no system launcher or global trust changes are included.

In v11, switching language changes presentation only and does not submit a device request. Runtime responses carry both language variants; the native client uses generated state translations if an older runtime response arrives in the previous language. The generated fallback is checked against the runtime source before builds and source packaging. Task phases, public detail keys and actionable errors are localized; unknown machine codes remain in diagnostic reports rather than appearing as untranslated prose.

The post-v12 source adds a blocking, scrollable progress dialog for known mutations, disables navigation and duplicate actions while they run, and returns to normal controls for errors and reboot requests. Dialog open/close callbacks reconcile fast completion during animation so an obsolete overlay cannot conceal recovery controls. The OS may still background the app; reopening queries its existing task. A recognized active older service now offers restore before its bundled update, and IMS/APN waiting explains the specific network dependency. These changes have SDK compile and code/state-machine review evidence; they are not in the immutable v12 BAR and have not yet passed physical UI acceptance.
