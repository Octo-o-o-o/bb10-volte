# Native mobile interaction contract

> Earlier public r20/mobile 0.1.0.15 scope is recorded in [RELEASE-r20](RELEASE-r20.md). Candidate and hardware results below remain version-specific.

The Cascades UI in `mobile/native` uses Qt 4 and C++98. The implementation is a client of protocol 2; it does not infer Root access, carrier readiness or installation eligibility from an icon, network label or an earlier UI step.

Current integrated candidate: mobile **0.1.0.19 / desktop and service r21**. Historical Q20/Passport lifecycles and SIM changes remain scoped to their recorded versions. After a fresh Q10 Root, mobile v18/r18 passed owner-reported calls, SMS and saved acceptance but browsing on Telecom 4G failed. The exact r21 proxy correction was separately verified on Passport/Telecom; the Q10 correction has not been physically retested. See [validation](MOBILE-VALIDATION.md).

Later, unreleased source makes call checks optional and clarifies automatic startup. The released 0.1.0.19 BAR retains its earlier wording; these changes do not alter the background service's startup mechanism.

## Home and tasks

Home shows the hardware, carrier, current state, reason and one primary action returned by the runtime. First activation exposes the backup destination before confirmation. An available SD card is preferred on first use; internal storage remains possible and is explicitly described as a copy on the same phone. The runtime chooses the exact owned export path and performs readback verification.

Device mutations return a persistent job identifier. The app saves that identifier and follows the existing job while the explicitly requested operation runs, displaying translated stages without inventing percentage progress. Closing the UI does not cancel the Root worker. After reopening, one unambiguous saved task is checked once in the foreground; the user can check the same task manually, never submit a second install command. A timeout preserves the operation identifier; only the matching durable job can settle it. A missing job file remains unknown because the original request may still arrive. Restart instructions come from device state rather than a UI restart counter. A second carrier-policy restart is distinct from installation or service-update restarts. An explicitly checked completed task can trigger a fresh status read. A one-shot observation without live state instead asks for a manual status check; it never invents network readiness. Export locations and report feedback remain available. The manual call record is a synchronous, guarded response with no background job.

Post-v12 source addresses a Q20 save-feedback failure: the four checks were saved, but the UI did not confirm the result until reopening. Saving returns the observation already validated under the management lock instead of repeating a full probe after the write. A missing response triggers one observation during the active session, never another save or a radio change; that observation may update internal context metadata. After reopening, checking is explicit. The pending confirmation type and opaque context survive reopening. A current observation either confirms the record or tells the user to check the boxes and save again; changed context clears the boxes. A different boot, SIM or payload cannot inherit the old check, and another management task cannot erase the unresolved confirmation. Saving and checking have distinct bilingual progress messages.

The v17 source candidate reuses fully verified private snapshot evidence only within the same foreground request, reducing repeated component reads for checks and management actions while still probing the current device before a call confirmation. A successful confirmation is shown beside the button and cannot be submitted again for that verified context. A missing or contradictory job response retains the original operation for checking; a completed task with a failed subsequent phone probe is shown as two separate results. Phone timing, QNX compatibility and the v17 UI require their own device acceptance.

In v18, a matching existing private snapshot is fully reverified for execution without rereading the unused application source bodies. Signed metadata and directory layout are checked before an older, rejected active snapshot is skipped; its unused body is not fully checked on this path. Initial snapshot creation still fully verifies the source. During a refresh, the interface labels information left on the page as preceding the current check. New-version first-use and warm timings require separate phone measurements.

On QNX, the mobile worker uses the dedicated `SPAWN_NEWAPP` launcher. A controlled Passport probe verified `appid = sid = pid` and completion after the parent exited; ordinary fork/setsid alone is not the application-lifecycle guarantee. Closing and reopening the real app still requires the separate UI acceptance check. Existing tasks survive app replacement. v8 automatically completed a pre-existing stop task after a real reboot and then offered the bundled update; the owner also completed that update through the native UI.

Registration and verified calls remain separate. Once the service is connected, the main action checks status; recording the four manual call checks is optional and does not enable calling. The optional page records outgoing and incoming calls, audio in both directions and LTE without placing calls. The backend binds the record to the current SIM, boot and payload; a changed context invalidates the record, not normal calling. The client submits the four booleans at the top level of protocol 2 along with `confirmed` and the opaque `call_context`, and clears the checkboxes whenever that context changes. Cached observations and responses from older runtimes also keep the check as a secondary action.

## Management, offline access and recovery

The management page provides language, backup destination, offline ZIP selection, update check, diagnostics, compatibility, enable, disable/restore, rollback and full uninstall. The system file picker only supplies a path; the runtime still copies and verifies the package in its private directory before use. Online metadata and downloads use HTTPS with normal certificate verification and an explicit project-domain allowlist. Download size and hash checks do not replace the runtime's publisher signature verification. Update comparison shows the signed runtime and BAR versions separately. An online runtime update binds the metadata version and hash to the bytes the signed verifier actually parses; a newer BAR still requires separate installation. No online access is required for the bundled installation or offline update path. Diagnostics and compatibility reports may return synchronously without taking over a pending write job; their exact exported location remains visible on Home and in management details after reopening the app.

In the v17 source candidate, update and file-picker feedback is shown alongside the update controls without erasing a separate phone or task error. A network check or download can be cancelled before installation begins; an already submitted Root task cannot be cancelled that way. Cancelling the bundled-update confirmation keeps an existing offline selection, while an invalid new selection clears the old package. These interactions need device UI acceptance.

When an old r14, r15, r16 or r17 service is stopped, restored and ready to update, the home primary action and management page offer the **bundled update**. It applies the signed payload already in the BAR without choosing an offline ZIP. Ordinary ZIP updates require a newer runtime version; selecting the same-version ZIP is not the old-engine adoption path. Each old-service migration to the current r21 payload requires its own evidence.

Destructive operations use a cancellable system confirmation describing the changes and required restarts. Button eligibility comes from the runtime's action list. While a job is running the UI does not submit another mutation. Full uninstall is a restoration workflow; deleting the app icon alone is not represented as service removal.

The separate experimental page has 23 explicit options: four existing carrier profiles (`china-mobile`, `china-unicom`, `china-telecom`, `china-telecom-46011`) and 19 exact-variant trial profiles/catalog entries generated from the shared desktop definitions and signed in the bundle. The trials comprise 13 controlled manual candidates and six read-only Passport combinations. Generic legacy profiles are limited to SQN100-3, SQC100-2 and SQW100-4; every other variant requires its exact trial. The page sends `experimental=true`, explains the lack of hardware acceptance and leaves autostart disabled. Changing a profile clears prior eligibility and requires a fresh check. Every legacy start independently rechecks compatibility and the installed profile. A completed experimental task refreshes its selected profile. It is never the normal activation button; native hashes, ABI, current SIM, network and recovery remain backend gates.

Legacy controls have their own scope. `legacy-stop` disables the old autostart entry and waits for restoration. `legacy-update` requires a stopped/restored installation and no pending install-transaction before calling the existing updater; interrupted transactions remain and blind retries are rejected. `legacy-uninstall` removes legacy startup entries while retaining private payloads/backups. It is not automatic protocol-2 full removal, and no legacy rollback is offered. The 13 ordinary trials have no Telecom attach modification: their restoration source is the PPS journal captured at startup, not an automatic protocol-2 original-file export receipt. Exported trial results are labelled `last_checked_not_live`, not presented as live status or call acceptance. Read-only Passport options do not expose mutations.

## Language and screen behavior

Menus, Root/transport errors and confirmations have Chinese and English strings in `src/ui_strings.h`; runtime state text uses the requested language in its display model. Language changes only update presentation. Every content page scrolls vertically, body and error labels wrap, and diagnostic text is plain text. The UI uses full-width actions, normal Cascades focus behavior and the R refresh shortcut. Confirmation can be cancelled through the system dialog.

The source after mobile 0.1.0.19 requests that the screen stay awake while the app is fullscreen. On thumbnail or invisible transitions it restores the normal screen idle mode, and requests keep-awake again on return to fullscreen. This controls idle behavior, not the phone's manual power or lock controls. It is not present in the previously released 0.1.0.19 BAR and needs acceptance on a phone with a newly built BAR.

Acceptance must cover the Q10/Classic smaller square screen and Passport larger square screen in both languages, physical keyboard/trackpad navigation where present, touch, long messages, FilePicker cancellation, Root unavailable, backup selection, installation interruption, both restart stages, offline update failure and reopening an existing task. Compile or static-contract tests do not establish those physical UI results. Added portrait devices require their own layout and functional acceptance.

For the new screen behavior, leave the app fullscreen without touching it for longer than the configured display timeout; check that the screen remains on. Minimize it and repeat, then return to the app and repeat again. Also check that the normal power/lock control still works and that closing the app restores the phone's normal idle behavior. Record the BAR version, device and results independently from the 0.1.0.19 acceptance record.

## Build and trust

The BAR identity is `com.octolab.bb10volte`, author `OctoLab`, with a fixed author ID. The build pins the entry script SHA-256 into `bundle_identity.h`; the UI checks the original bytes before invoking `/bin/__root`. It sends those exact bytes through a literal, collision-checked heredoc into an exclusively created random Root-private directory. Only that private copy is pathtrusted and executed; the app's writable source path is never reopened as executable code after verification. The source assets directory is passed as data for the entry's independent signed-bundle verification. The helper receives a fixed minimal environment, an allowlisted action and base64 JSON. Cleanup unlinks only its own entry and removes its own empty directory. Device Python runs from a trusted file, not stdin. Entry source must end with LF and contain no NUL so the literal transfer preserves its bytes. An incomplete UI-only build has no valid entry hash and refuses device operations.

Build checks include ARM32/QNX ELF, libraries, BAR identity and assets. v6 through v10 have matching SUD success and actual registered versions; future candidates still need independent verification. Runtime payload and native application versions are separate.
Ordinary opening, returning to the foreground and unlocking show a labelled last observation without starting a status check. One valid, unambiguous saved task receives one foreground poll; malformed or conflicting identities are retained for diagnostics. The first launch without a cache also requests one manual check, since old versions have no reliable first-launch marker. Network, reboot and Root waits are checked manually; an explicitly requested active job may still be polled in the foreground. Cached information cannot authorize a device mutation, and call confirmation revalidates boot, SIM and IMS under the job and management locks. The Root request times out after 150 seconds without verified progress and has a 15-minute total limit; independent lower-level timeouts remain unchanged. A failed probe retains an existing cache and does not claim the device is unsupported. Unknown write outcomes never trigger automatic resubmission.

Before process startup, the unsigned BAR depends on AutoRoot launcher initialization. The app cannot render a waiting page while the OS refuses its launch. The enabled automatic service has its own boot entry; ordinary restarts do not require opening the app. When checking status, managing the service or continuing an unfinished task, wait for the Root success notification before opening the app. Repeated early launches produced an observed Navigator deadlock; no system launcher or global trust changes are included.

In v11, switching language changes presentation only and does not submit a device request. Runtime responses carry both language variants; the native client uses generated state translations if an older runtime response arrives in the previous language. The generated fallback is checked against the runtime source before builds and source packaging. Task phases, public detail keys and actionable errors are localized; unknown machine codes remain in diagnostic reports rather than appearing as untranslated prose.

The post-v12 source adds a blocking, scrollable progress dialog for known mutations, disables navigation and duplicate actions while they run, and returns to normal controls for errors and reboot requests. Dialog open/close callbacks reconcile fast completion during animation so an obsolete overlay cannot conceal recovery controls. The OS may still background the app; after reopening, the user checks its existing task. A recognized active older service now offers restore before its bundled update, and IMS/APN waiting explains the specific network dependency. These changes are not in the immutable v12 BAR and need version-specific physical UI acceptance.

Progress markers are emitted only after actual verified-file or trust steps finish. The foreground request uses a 150-second idle deadline and a 15-minute total limit; elapsed time and a missing response do not establish whether a detached operation completed. An interrupted manual backup export is reported separately and does not block device changes, while an unconfirmed device mutation keeps its original identity.

A guarded BAR never switches its management worker back to a signed older worker that lacks unknown-outcome protection. An older multi-stage job whose worker cannot be verified is retained for diagnosis, not restarted. A service rollback may keep the newer management component; a runtime-only rollback to an unguarded worker is refused. Manually reinstalling an old BAR restores that old BAR’s limitations and is outside the new protection.
