# 批量收机：先试测、集中验收、按证据登记

2026-11-07 起，机主希望加快多台设备适配。已有清空授权继续有效；优先使用现有系统和 Root。每台仍按完整后缀、板型、OS、实际 SIM 归属网络独立登记。携转号码按实际 SIM 识别。

1. **一次收机检查。** 读取身份、系统、Root、六个原生文件指纹、LTE/数据、现有服务及恢复条件。生成本台私有绑定和原配置备份。不要每换一张卡就重复配对、刷机、制作恢复镜像。
2. **先复用候选。** 原生基线一致、已有恢复实现的组合，使用同一个冻结引擎，准备本台的精确试测范围。候选可以涵盖计划测试的卡，公开支持仍按已通过的组合登记。未知原生文件、板型冲突或未实现的恢复流程进入专项适配。
3. **每张卡一轮集中测试。** 自动读取注册、LTE、备份、启动、短信忙状态和通话状态；机主一次集中确认呼入/呼出、双向声音、通话数据、短/长短信及两条相同内容短信。观察开始后再测试。已注册本身不能填写声音或实际收信通过。
4. **按实际状态重启。** 保存策略或释放旧提供器时保留正常重启；如果策略已生效且当前启动已经连接，就继续测试。恢复路径按本台、本引擎实际做一次完整核验，其他卡的已验证部分可引用原证据并注明版本，出现差异再补测。
5. **自动汇总证据。** `tools/intake_acceptance.py` 对 17 项检查核对文件哈希和完整型号/板型/系统/PLMN，自动输出已适配、带短信限制、待补测、失败或待产品集成。未做项目保持未知。每条结论保存来源、版本和复用范围；工具不从日志推断双向声音或可见消息条数。
6. **集中同步和出包。** 同一设备计划内运营商测试完后，统一同步共享运行限制、桌面目录、手机版目录/标签、文档，再构建一组候选。最终包做安装、启动、页面和基本通话/短信复核；相同代码不因单张 SIM 通过反复出包。多个设备可以共用同一发行批次，个别设备的问题单独记录。

验证清单保存为 JSON。`sources` 只保存案例目录内的相对路径和 SHA-256；`checks` 用 JSON Pointer 引用原始验收记录里的布尔事实。`scope_note` 明确测试版本，引用旧版本时明确写明，不自动声称全部项目在最新包重测。

```powershell
python tools/intake_acceptance.py --manifest <本案例清单.json> --evidence-root <本案例目录> --output <新的判定.json> --registry materials/device-intake-validation.json
```

示例真实案例是 SQW100-1／移动 460-00 的 `477b-mobile00-acceptance-input.json`，输入证据包含 436、464、475、476。汇总登记在 `materials/device-intake-validation.json`。最初清单引用了错误的字段名，479 检查拒绝登记；修正引用后 479b／480 通过，原始输入和失败记录保留。

`adapted` 表示证据要求通过且项目现有精确运行范围已允许；新型号若测试通过但产品范围尚未同步，会得到 `validated_pending_integration`，随后由当前适配会话完成一次集成和构建。工具本身不连接手机、不修改型号白名单、不发布软件。它是收机工作流工具，未增加手机客户端上的自动认证按钮。

短信例外只接受同一完整型号、板型、系统和运营商下有来源的机主授权，并单列失败或未知的短信项。不能用该例外跳过身份、备份、恢复、语音或数据验证。SQW100-1 的电信已知短信问题继续保留，不继承为其他型号的授权。

此次 SQW100-1 的大量重复操作还包括：首次电脑配对修复、换入无效电信卡后的对照、短信故障取证、旧手机版升级识别修正，以及逐运营商多次打包。这些处理不作为后续每台设备的固定步骤。配置明细见 [SQW100-1 改动对照](SQW100-1-CONFIGURATION-DELTA.md)。
